Sección 01

La Bala Trazadora

Estrategia de exploración y mitigación de riesgo inicial

Antes de escribir una línea de código, el equipo ejecutó la skill grill-me para interrogar el problema desde múltiples ángulos. Esta fase no buscaba diseñar la solución definitiva, sino exponer los supuestos incorrectos que ya operaban silenciosamente en el equipo.

El árbol de diseño generado reveló tensiones que no habíamos anticipado. El primer supuesto erróneo era que un usuario tiene una quincena activa a la vez. La realidad: los usuarios necesitan navegar historial de quincenas anteriores para comparar patrones de gasto, lo que redefinió el modelo de datos desde el principio. El segundo supuesto erróneo era que el ingreso mensual se divide en exactamente 50/50 entre quincenas — en Colombia muchos salarios llegan el 15 y el 30 en proporciones variables, lo que forzó el campo porcentaje_primera_quincena en el modelo IngresoMensual.

La Bala Trazadora aplicada

El issue más incierto del sistema no era autenticación (problema resuelto) ni los formularios del frontend (UI trivial). Era la integración entre la lógica de quincenas y los recordatorios de deudas: ¿cómo sabe el sistema que una deuda con fecha_vencimiento = 2025-06-14 pertenece a la primera quincena de junio y debe marcarse como urgente si faltan 2 días?

Decisión de Bala Trazadora
Se instruyó a Ralph para atacar primero el Issue #007 (ingresos mensuales) junto con el #001 (auth), forzando la definición de ingreso_service.py y su función fechas_quincena() como primer artefacto de código. Esto validó el modelo de datos central antes de construir cualquier otra capa. El Handoff #1 documenta esta decisión explícitamente.

Sección 02

Anatomía de la Complejidad

Módulos Profundos vs. Superficiales — análisis bajo Ousterhout

John Ousterhout define un módulo profundo como aquel cuya interfaz es significativamente más simple que su implementación: oculta complejidad vasta detrás de una superficie estrecha. Un módulo superficial no oculta nada — quien lo usa absorbe la complejidad en lugar de encapsularla.

Módulos Profundos Los mejores diseños del agente

El módulo más elegante producido por Ralph es ingreso_service.py. Observemos su interfaz pública completa:

ingreso_service.py — interfaz pública (5 funciones)
# Interfaz completa del módulo

ingreso_primera_quincena(monto_mensual: Decimal, porcentaje: int) → Decimal
ingreso_segunda_quincena(monto_mensual: Decimal, porcentaje: int) → Decimal
calcular_ingreso_quincena(ingresos_activos: list, numero_quincena: int) → Decimal
fechas_quincena(anio: int, mes: int, numero: int) → tuple[date, date]
total_ingresos_mensuales(ingresos_activos: list) → Decimal

Detrás de esas 5 firmas se esconde: manejo de Decimal para evitar errores de punto flotante en montos financieros, uso de calendar.monthrange() para calcular el último día de cualquier mes (incluyendo años bisiestos), y validación de que numero_quincena solo acepta 1 o 2. El llamador no sabe nada de esto.

Diagnóstico Ousterhout — Módulo Profundo
ingreso_service.py pasa la prueba del "costo de la interfaz": aprender las 5 firmas cuesta mucho menos que reimplementar la lógica de fechas y distribución en cada sitio que la necesite. El test test_fechas_segunda_quincena_bisiesto confirma que la complejidad del calendario (año 2024, febrero, 29 días) está completamente oculta al consumidor.

Módulos Superficiales Los puntos donde la IA falló

Ralph exhibió un patrón problemático recurrente: la tendencia a crear un archivo separado por cada responsabilidad conceptual, aunque esa responsabilidad fuera trivial. El checkpoint arquitectónico documentó este problema explícitamente:

Problema detectado en el checkpoint — helper duplicado
# ❌ La misma función en DOS archivos distintos

# backend/app/api/gastos.py
def get_quincena_del_usuario(db, quincena_id, user):
    return db.query(Quincena).filter(
        Quincena.id == quincena_id,
        Quincena.user_id == user.id
    ).first()

# backend/app/api/deudas.py — COPIA EXACTA
def get_quincena_del_usuario(db, quincena_id, user):
    return db.query(Quincena).filter(
        Quincena.id == quincena_id,
        Quincena.user_id == user.id
    ).first()

El checkpoint también identificó que Base = DeclarativeBase() vivía dentro de models/user.py, creando una dependencia implícita: todos los modelos importaban Base desde el modelo de usuario, lo que significa que un cambio en user.py podía romper las importaciones de quincena.py, gasto.py y deuda.py.

Diagnóstico Ousterhout — Módulo Superficial
Ousterhout describe este anti-patrón como "classitis": la creencia de que más archivos pequeños equivale a mejor diseño. En realidad, cada archivo que solo re-exporta o duplica sin añadir valor incrementa la complejidad de interfaces. La solución aplicada fue mover Base a db/base.py y centralizar el helper en services/quincena_service.py.

Fuga de Información Detalles internos que escaparon a la UI

El Handoff #2 establece explícitamente: "El frontend debe consumir exclusivamente la API REST. No compartir lógica de negocio entre frontend y backend." Esta regla nació de un episodio concreto de fuga de información en el componente DeudaItem.tsx:

❌ Fuga de implementación — versión inicial
// DeudaItem.tsx — lógica de negocio en la UI
const diasRestantes = differenceInDays(
  parseISO(deuda.fecha_vencimiento), new Date()
);
const urgencia = diasRestantes <= 3 ? 'urgente'
  : diasRestantes <= 7 ? 'proximo'
  : 'a_tiempo';
✅ Corrección — ocultamiento de información restaurado
# recordatorio_service.py — lógica donde pertenece
def clasificar_urgencia(fecha_vencimiento: date, hoy: date) → str:
    dias = (fecha_vencimiento - hoy).days
    if dias <= 0:
        return "urgente"
    elif dias <= 3:
        return "proximo"
    return "a_tiempo"

# El API devuelve urgencia pre-calculada
# El frontend solo lee deuda.urgencia
Lección de Ousterhout aplicada
La fuga ocurre cuando la misma decisión de diseño afecta múltiples módulos. Los umbrales de urgencia (3 días, 7 días) eran una decisión que vivía simultáneamente en backend y frontend. Consolidarla en recordatorio_service.py es la materialización práctica del principio de ocultamiento de información.
Sección 03

El Veredicto Retrospectivo

Post-mortem de la skill /improve-codebase-architecture

Tras completar los issues #001 y #007, se ejecutó la skill /improve-codebase-architecture que desplegó tres sub-agentes paralelos con posturas radicalmente distintas. El checkpoint arquitectónico documenta en detalle cada propuesta.

"El debate entre sub-agentes no fue sobre quién tenía razón — fue sobre qué tipo de cambio futuro era más probable y cuál interfaz lo absorbería mejor."
Sub-agente A — Separación estricta

Propuso una capa nueva domain/ con clases estáticas. Máxima separación, pero excesiva para un MVP. Introduce complejidad de navegación innecesaria.

Sub-agente B — Services como verdad única

Mover toda lógica a services/ sin capas nuevas. Consistente con la arquitectura existente. Resuelve los 3 problemas sin overhead. Ganó.

Sub-agente C — Módulo utils/

Propuso un módulo de utilidades compartidas. El riesgo: utils/ suele convertirse en un cajón de sastre que dificulta encontrar lógica de negocio específica. Descartado.

Solución híbrida implementada
Base declarativa → db/base.py (Sub-agente A y B coinciden). Lógica de fechas → services/quincena_service.py (Sub-agente B). Helper de ownership → centralizado en quincena_service.py (Sub-agente B). Resultado: sin capas nuevas, sin duplicación, sin acoplamiento implícito.

Impacto en la velocidad del sprint

⚡

Issues #001–#002 (pre-debate)

Velocidad variable. Auth rápido, pero el modelo de quincenas requirió iteración por la lógica de fechas mal ubicada en el router.

🎯

Issues #003–#007 (post-debate)

Velocidad notablemente más alta. Con quincena_service.py centralizado y Base aislada, los últimos issues se completaron sin retroalimentación negativa.

🔁

Change Amplification observada

El issue #007 requirió modificar solo models/ingreso.py, ingreso_service.py y un endpoint nuevo. La interfaz absorbió el cambio en 3 archivos.

📐

Elasticidad de la interfaz

El campo porcentaje_primera_quincena con default 50 resultó elástico: cuando llegó el requerimiento de distribución asimétrica, el modelo ya lo soportaba sin cambiar el esquema.

¿Demostró la interfaz buen gusto arquitectónico?

Decisiones que envejecieron bien
El campo porcentaje_primera_quincena, la separación entre IngresoMensual (fuente recurrente) y Quincena.ingresos (ingreso real recibido), y fechas_quincena() como abstracción de calendario pura.
Decisiones con fragilidad potencial
La FK directa Gasto → Quincena hace difícil mover un gasto entre quincenas si el usuario lo registró incorrectamente. Requeriría cambios en múltiples capas.

El debate de los sub-agentes demostró ser valioso no por producir una propuesta radical (que habría sido contraproducente en pleno sprint), sino por forzar al equipo a articular explícitamente cuáles cambios futuros son probables. Esa articulación es precisamente lo que Ousterhout llama diseño de interfaces: no optimizar para la implementación de hoy, sino para el cambio de mañana.

Conclusión retrospectiva
FinanzApp demuestra que la co-creación hombre-máquina con un agente LLM produce módulos profundos genuinos cuando el humano interviene para corregir la tendencia natural del agente hacia la atomización excesiva y la duplicación. La arquitectura resultante es honesta en el sentido de Ousterhout: expone su complejidad real en el lugar correcto, y no la esconde en capas de indirección vacía.
